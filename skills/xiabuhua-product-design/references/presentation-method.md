# Main-controller method for presentations

Use for a new or substantially revised presentation. The main design workflow owns direction, narrative composition and visual acceptance. Route to `html-deck-runtime` only for a fixed-stage HTML deck or page-by-page print/PDF; its PPTX helper can inventory basic text, geometry and images for a separately specified rebuild, but does not convert legacy PPT or reproduce PowerPoint fidelity. It receives a resolved specification and supplies execution mechanics only. A responsive explainer or scrolling narrative keeps its own web layout/runtime and does not inherit the fixed stage.

## Resolve the brief and direction

Use the shared [direction workflow](style-direction-workflow.md) after the minimum audience/content/runtime intake. Determine whether the deck is spoken, read asynchronously or converted from a source. Do not repeat questions already answered. Show a cover and a representative body/evidence specimen for each unresolved direction, then obtain the user's selection. Brand and presentation-origin examples in the reference branch are peers; delivery format gives no aesthetic source priority.

## Author the content blueprint

For each slide, record only what the assignment needs:

| Field | Main-controller decision |
| --- | --- |
| role and takeaway | What this slide enables the audience to understand, compare or do |
| content and evidence | Exact source content, quantitative basis, quote, example or clearly illustrative material |
| composition | Layout, hierarchy, relationships, assets and appearance derived from the selected direction |
| interaction/sequence | What appears or changes, on which trigger, and the observable result |
| next relation | Why the next slide follows and what context must persist |

Let the audience's question and the content determine order and density. Do not force every report into a persuasion story or every deck into the same title/cards/closing pattern. Keep limitations and denominators attached to relevant claims. Preserve the source's degree of certainty; a visual headline cannot promote a hypothesis to a finding.

## Dispatch resolved execution work

For a fixed-stage or paged output, give `html-deck-runtime` the agreed slide blueprint, content/asset files, authored layout specification, interaction instructions and delivery requirements. The authored layout includes the appearance decisions necessary to implement it; the executor does not create another selection process or derive a new theme. Candidate specimens are bounded execution tasks under the main workflow, not permission to build the complete deck. Keep responsive or scroll-based presentation execution in the parent web workflow.

The executor may fit supplied content within the agreed layout, implement navigation, resize the fixed stage uniformly, handle focus/input and check overflow. It returns a concrete incompatibility if a content or runtime constraint cannot be met. The main controller resolves changes that affect the selected design.

## Accept the result

Compare cover, representative dense/body content and the remaining sequence with the selected specimen. Check the narrative relationship, typography roles, material/assets, color hierarchy and motion against the main agreement. Record necessary adaptations instead of silently adopting an executor default.

Separately verify runtime evidence: every intended slide is reachable, stage geometry is correct, inactive content cannot intercept input, controls work and source content is intact. HTML, static PDF and editable PPTX are different deliverables; only run and claim the formats requested. A technical pass does not replace the main controller's visual/content acceptance.
