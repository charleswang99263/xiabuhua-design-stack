# Main-controller method for HTML reports

Use for quantitative, qualitative, research, strategy and mixed-evidence reports. A portable HTML report is not automatically a desktop application. Read this profile instead of `web-app-method.md` unless an actual ongoing operational workflow is part of the request.

## Identify the reader's task

- **Report:** understand a bounded body of evidence, inspect its limits, discuss implications or choose a next experiment/action.
- **Dashboard/workbench:** repeatedly monitor changing state or perform ongoing operational tasks across objects/workflows.

Filtering, a detail panel or an interactive chart does not by itself turn a report into a workbench. A report can have an outline and controls without invented workspace navigation, global app chrome or destinations outside its actual content. If the request is a hybrid, name its primary job and make the secondary use visible without letting it replace the primary reading/decision path.

## Set direction through the shared workflow

Use [style-direction-workflow.md](style-direction-workflow.md). Requirements, audience, evidence form and reading context determine candidates. All style/source families remain peers; reports do not mandate paper, neutral colors, a particular typeface or a fixed chart/card layout.

Every candidate specimen should show a central finding, a representative piece of evidence and its interpretation boundary. Keep the input data/content equal. Compare actual reading organization, density, typography/material and interaction, not three skins on an unchanged app shell. The chosen specimen is accepted by the user before full authoring.

## Compose evidence into a report

Plan the questions the reader needs answered, then assign an appropriate content form to each: argument, chart, table, annotated example, quote, chronology, comparison or test plan. Use only those the evidence supports. Do not insert a KPI row or dashboard shell merely because numeric data exists.

Make the principal conclusion and the evidence behind it easy to find. Place scope, definitions, sample limits and uncertainty near the relevant claims. Keep facts, interpretations, hypotheses and recommendations distinguishable. Allow readers to move from a summary to supporting evidence and return without losing the selected context.

Use the relevant Data Analytics capability when numerical validation or chart selection needs it. Preserve the user's explicitly selected HTML delivery and main direction while retaining source, scale, denominator and calculation requirements. A polished chart cannot establish source truth. A small qualitative sample cannot establish population prevalence or causal effects.

Interaction should help readers inspect or compare evidence, follow a causal argument, trace a source, or formulate a next action. State changes must be determined by the selected data, not randomized illustration. Local simulation, actual submission and persistent operational state are distinct claims.

## Dispatch and accept

The main workflow supplies the report argument, selected specimen, content/metric definitions, composition and interaction requirements. Component/execution references fill implementation details. Do not let their default shell become the report's identity.

Validate the initial reading path, one dense evidence section, a filtered/detail state and the narrow layout against the selected specimen. Inspect whether the result answers the requested report question, not merely whether every number has a card. When reusing an earlier report pattern, state the content/task reason; do not force novelty for its own sake.

Record the actual calculations, sources, interaction checks, rendered evidence and remaining limits. Do not claim that visual differentiation alone proves better user outcomes or reduced real-world rework.
