# UI Interaction Reference

Use this skill for intent-based pattern selection, implementation contracts and live reference adaptation. It does not
choose the product architecture or visual identity, and it is not a component
library to install wholesale.

## GSAP execution

When GSAP is explicitly selected or justified for coordinated timelines, scroll, SVG or imperative choreography, use [gsap-execution](references/gsap-execution.md). It owns the scoped implementation and official topic routing; the parent owns design intent, state and acceptance. It is bundled reference material, not an additional globally discovered skill or an installed animation runtime. Simple CSS or an established Motion implementation does not trigger this branch.

## Local tactile mechanisms

For a supported tactile job, read only the selected entry in the [canonical tactile contract](../html-ppt-component-museum/references/tactile-interactions.md) and its original primitive. It covers magnetic snap, velocity deformation, layered parallax, center focus, tabs, image expansion, gesture transition and bounded collisions. No external search or second router is needed for known local behavior. Specify trigger, state, cancellation and fallback in the parent agreement; do not create a competing style contract.

## Direction input

For authored motion, media preparation, timing diagnosis or measurement outside the common tactile set, use [the complete motion workflow index](../xiabuhua-product-design/references/motion-extended/index.md). Read a matching intent/recipe/tool entry only; do not traverse every branch or send known local mechanisms back to online research. The parent retains visual direction and final acceptance.

Receive the approved/inherited style agreement, selected specimen, task/content and delivery target before choosing implementation references. Pending direction permits only candidate specimens. If direction is missing, follow [the shared workflow](../xiabuhua-product-design/references/style-direction-workflow.md); do not let a component catalog choose it.

A component is a mechanism plus an adaptable visual treatment. Reject or restyle defaults that contradict the agreed type, composition, material, imagery or motion. If a required repair changes the selected identity, return evidence to the main design skill. Do not silently replace the identity or ask a second independent style question.

## Workflow

### 1. Define the component job

Describe the intended result before browsing:

- content or state being communicated
- user input and visible feedback
- passive, optional, or task-critical interaction
- target framework and existing component system
- viewport, input mode, accessibility, and performance constraints
- whether the component must work without motion or JavaScript

If the job is still vague, return to information architecture or art direction.

For local interaction refinements, read [interaction-pattern-selection.md](references/interaction-pattern-selection.md). Use its intent matrix to distinguish selection, reordering, disclosure, progress, dependent feedback and spatial/temporal effects before choosing a source. These ten patterns are options, not a closed menu. Keep logical state/commit separate from animation and use the supplied contract for implementation or a requested copyable prompt; a build request must not end at prompt delivery.

### 2. Choose a source

Reuse a suitable project primitive or verified local museum mechanism first. Browse external implementation sources when the local pattern does not cover the job; a reference-only pattern is not an already tested component.

Check the museum's [local effects index](../html-ppt-component-museum/references/local-effects-index.md) for supported APIs and tested boundaries. Verified original local effects do not require reopening React Bits on every reuse. Frequent large/complex mechanisms can be maintained locally too; online exploration is for missing capability, novel expression or a specifically requested high-craft target. After adapting and validating a repeated mechanism, promote its original implementation and lifecycle contract to the appropriate existing museum category.

When external exploration is needed, read `references/source-index.md`, then use the smallest suitable source:

- **Uiverse**: micro-controls, form details, loaders, switches, cards, and
  lightweight CSS/Tailwind effects.
- **React Bits**: expressive React animation, text, background, 3D, canvas, and
  interaction primitives.
- **Aceternity UI**: high-impact marketing, hero, editorial storytelling, and
  landing-page sections.
- **Motion official examples/docs**: state feedback, layout/reorder, shared elements and presence; use mechanisms with project-owned styling.

Use live official pages because catalogs, dependencies, and licenses can
change. Use `anysearch` first for discovery, then built-in web when unavailable or insufficient; use official GitHub or item documentation for verification. Do not repeatedly probe a known-unavailable search runtime.

### 3. Inspect candidates

For each serious candidate, inspect the exact item page and source code. Record:

| Field | Required decision |
| --- | --- |
| Communication job | What becomes clearer or easier |
| Input and feedback | What the user does and what visibly changes |
| Direction fit | Approved specimen, compatible facets, conflicts and permitted adaptations |
| Adaptation | What must change to fit the project system |
| Dependencies | Runtime packages, bundle cost, client-only constraints |
| States | Default, loading, error, disabled, focus, selected as applicable |
| Accessibility | Semantics, keyboard, focus, contrast, reduced motion |
| Responsive behavior | Narrow layouts, touch, pointer, text scaling |
| Performance | Main-thread, canvas/WebGL, media, list, and battery impact |
| License | Free/pro status, attribution, redistribution restrictions |
| Verification | Exact URL/version/date, code vs rendered evidence, untested boundaries |

Reject a candidate when the explanation value does not justify its complexity.

### 4. Adapt, do not paste

- Translate colors, type, radius, spacing, and content into project tokens.
- Preserve useful interaction logic while changing recognizable styling.
- Reuse the project's primitives and state model when possible.
- Isolate heavy effects and lazy-load them when they are not task-critical.
- Add a designed reduced-motion or static variant.
- Keep visible controls operable with keyboard and touch.
- Coordinate the number and intensity of patterns with the approved direction and task rhythm. No mandatory effect quota; zero effects can be correct.

### 5. Verify the rendered result

Test representative desktop and mobile viewports, keyboard and touch behavior,
reduced motion, loading and error paths, console output, and realistic content.
Compare the mechanism and its visual treatment with the selected specimen. Confirm it contributes to understanding, feedback or the approved identity. Check content-bearing marks are stable when data is unchanged, JavaScript loops respect reduced motion/visibility, and keyboard/touch have meaningful outcomes.

## Relationship To Other Skills

- `xiabuhua-product-design` owns the product method, system, and quality bar.
- `brand-style-reference` supplies macro visual-language references.
- `html-ppt-component-museum` selects narrative component patterns for slides,
  reports, demos, and explainers.
- `ui-interaction-reference` finds concrete external implementation precedents
  after the component job is known.
- `html-deck-runtime` implements the supplied fixed-stage runtime and navigation; the main design workflow owns direction and narrative composition.

For HTML PPT work, the parent resolves narrative and visual direction first. Consult the museum only when a mechanism is needed; consult this skill only for a demonstrated specification/reference gap. Then pass the assembled blueprint to `html-deck-runtime` for stage and navigation execution. A static deck does not require either component branch.
Treat React-based sources as implementation references unless the deck already
uses React. Preserve the deck's single-file, no-build constraint by default.

## Safety And Licensing

- Do not install a library or copy code until the exact item, dependencies, and
  license are verified.
- Do not use paid Aceternity blocks or templates without explicit user approval
  and a valid license.
- React Bits may be used in end products but its Commons Clause prohibits
  reselling or redistributing the components themselves.
- Uiverse items are community-authored; verify the item license and original
  creator before reuse.
- Never turn collected components into a redistributed competing library.
